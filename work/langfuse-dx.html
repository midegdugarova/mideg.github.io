Langfuse Docs: friction notes from a first run.

Real friction I hit while building against the Langfuse Python SDK, written the way I'd open a docs PR: what happened, where the mental model broke, and the smallest change I'd make.

Python SDK · OpenTelemetry instrumentation · verified against current docs

I kept these notes while building the demo repo rather than reconstructing the experience afterwards.

None of the problems below is really about a missing API. The SDK worked. Authentication worked. Tracing worked. Prompt linking worked.

The friction appeared where the system's internal behaviour and the developer's observable symptom pointed to different explanations.

1. flush() is documented, but the failure mode is too easy to miss

What happened

My first quickstart script ran cleanly, printed the model's answer, and exited 0 — but no trace showed up in the dashboard.

Langfuse batches events and sends them asynchronously. A short-lived process can exit before those events are flushed.

The fix is one line: 

langfuse.flush()

But until you know that, the natural diagnosis is “my auth is wrong” or “the SDK is broken,” so you start debugging the wrong layer.

Where the docs fall short

The quickstart already includes langfuse.flush(), so this isn't a missing-documentation problem.

The issue is framing. The line reads as lifecycle guidance rather than as the fix for the most confusing first-run symptom:

The program worked, but nothing appeared in Langfuse.

Proposed fix

⚠️ Script finished successfully, but no trace appeared?

Langfuse sends events asynchronously. In short-lived scripts, notebooks, and CLIs, the process may exit before buffered events are sent — even when authentication succeeded and your code ran correctly.

Call langfuse.flush() or langfuse.shutdown() before the process exits. Long-running servers normally do not need this on every request.

The useful change isn't documenting another API. It's connecting the API to the failure state the developer is actually looking at.

2. Prompt linking through auto-instrumentation was non-obvious

What happened

After an eval experiment, I promoted the winning prompt into Langfuse prompt management and wanted every production trace to record which prompt version produced it.

My pipeline instruments Anthropic through OpenTelemetry: 

AnthropicInstrumentor()

That means application code does not manually construct the Langfuse generation containing the model call.

The obvious prompt-linking pattern uses: 

with langfuse.start_as_current_observation(
    as_type="generation",
    prompt=prompt,
) as generation:
    ...

That maps cleanly to manually-created generations. It doesn't map as naturally to auto-instrumentation because there is no generation object in application code to pass prompt= into.

The working pattern was: 

with langfuse.propagate_attributes(prompt=prompt):
    ...

Status

The current Langfuse docs now explicitly describe third-party instrumentation as a reason to use propagation.

So I would not file the original issue against the current page. The gap I hit has effectively been closed.

Remaining improvement

I'd still surface the decision earlier:

How is your generation created?

Your code creates it → attach prompt= directly.

An integration or OpenTelemetry instrumentor creates it → propagate the prompt around the instrumented call.

That distinction is more useful to a first-time user than organizing the choice around how many generations happen to share the prompt.

3. LANGFUSE_HOST vs. LANGFUSE_BASE_URL creates avoidable setup ambiguity

What happened

While wiring the demo repo, I encountered both names in the surrounding Langfuse ecosystem and added a defensive compatibility check: 

base_url = (
    os.getenv("LANGFUSE_BASE_URL")
    or os.getenv("LANGFUSE_HOST")
)

The current SDK naming is base_url / LANGFUSE_BASE_URL, while older host terminology remains supported for compatibility.

Nothing actually broke.

But first-run configuration is exactly where two names for the same concept create unnecessary uncertainty:

Are these aliases?
Did the SDK change?
Does one apply only to self-hosting?
Am I reading an outdated example?

Proposed fix

Standardize current first-party examples on: 

LANGFUSE_BASE_URL=

And whenever the legacy name appears, make the relationship explicit:

LANGFUSE_HOST is a legacy alias retained for backwards compatibility. New integrations should use LANGFUSE_BASE_URL.

That removes the need for users to infer whether the two names have different semantics.

What these issues have in common

None of them is a missing-feature problem.

The SDK worked. The APIs existed. Compatibility paths were present.

The friction came from the gap between what the system was doing internally and what a new user could infer from the symptom in front of them.

That's the part of developer documentation I care about most: not whether every method exists in the reference, but whether the docs intercept the wrong mental model before the developer loses twenty minutes debugging a system that is behaving exactly as designed.

These notes came directly from building the demo repo, not from reading the docs looking for things to criticize.
