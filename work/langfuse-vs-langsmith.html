Product / Competitive Analysis

The trace-to-eval loop is table stakes. Where it runs is the actual decision.

Langfuse vs. LangSmith, judged on one workflow: how you get from “I saw a bad answer in production” to “I have a regression test that guards against it.”

Hands-on Langfuse · LangSmith researched from current docs · August 2026

Every LLM observability vendor sells you on evals now. The demo is always the same: here's a trace, here's a score, here's a dataset, look how easy. So I picked the one workflow that actually matters day to day — the closed loop from a bad trace to a regression test — and built it end to end in Langfuse, then traced the same path through LangSmith's current docs to see where they really diverge.

The answer surprised me. The loop itself is nearly identical in both. The difference that matters is somewhere the demos never point.

I'm holding this to two tools on purpose. Phoenix/Arize, Braintrust, and generic OpenTelemetry-based stacks all close some version of this loop too. But Langfuse and LangSmith are the closest all-in-one comparison, and narrowing to two is what lets this go deep instead of wide.

Method: what's tested vs. what's researched

Being explicit, because it changes how much you should trust each half:

Langfuse: hands-on. I built the full loop — instrumented a small RAG pipeline using the Python SDK v4 and OpenTelemetry, captured traces, created an 8-item dataset, wrote two evaluators, and ran a two-variant experiment with side-by-side scored runs. Every Langfuse step below, I actually ran.

LangSmith: documentation-based. I traced the equivalent workflow through LangChain's current docs but did not run it against a live account. Where I'm inferring, I say so. Treat the LangSmith column as “what the docs describe,” not “what I stopwatch timed.”

That asymmetry is a real limitation of this piece. It's also the honest state of it, and I'd rather show the seams than pretend I benchmarked both.

The loop, side by side

Step Langfuse — ran it LangSmith — from docs
1. Get the trace Instrument the app; SDK ships spans and generations. Framework-agnostic. Auto-tracing, especially tight if you're on LangChain/LangGraph.
2. Spot the bad one Filter traces by tag/session, open the tree. Filter runs in the Runs tab, open the run.
3. Trace → dataset “Add to dataset” from the UI, or create_dataset_item in code. “Add to → Dataset” from the run view.
4. Define scoring A task function + evaluators using run_experiment. Evaluators + evaluate() over the dataset.
5. Run + compare Scored runs compared side by side. Experiment compared against past runs; CI gating is documented.

Read that table honestly, and mind the asymmetry: I ran the Langfuse column and read the LangSmith one. So I won't call it a tie in measured UX. What I can say is narrower and still decisive: on documented mechanics, the two loops are very close.

Both capture a trace, promote it into a dataset in roughly one action, attach LLM-judge and code-based scorers, and produce comparable experiment runs.

If anything the lean may go the other way for a LangChain-native team: LangSmith's “add run to dataset” UX is very direct, and step 1 costs almost nothing when the framework already understands the execution graph.

Anyone claiming Langfuse closes the loop in dramatically fewer steps is selling.

One real result from the loop:

I tested whether a “grounding-hardened” answer prompt improved faithfulness on an 8-item dataset.

It didn't.

Groundedness was identical to the terse baseline, while the hardened prompt added 38 system tokens per call — about 2.7× the baseline system prompt — for zero measured gain.

The value of the loop wasn't a win. It was cheaply disproving a plausible-sounding change before it shipped.

Where they actually diverge: where the loop is allowed to run

The loop is the same. The substrate underneath it is not.

Langfuse is MIT-licensed and self-hostable as a first-class path. The same core stack can run in Langfuse Cloud or inside your own infrastructure.

That means the closed loop — traces, datasets, evaluators, experiment history — can live inside the same data boundary as the production system.

For a team handling regulated or highly sensitive data, that changes the decision completely. The trace-to-eval loop reads the exact prompts, completions, metadata, and context that are most likely to contain sensitive information.

A perfect eval workflow you cannot legally point at production data isn't a workflow you can use.

LangSmith is proprietary and cloud-first. Self-hosting exists at the enterprise level rather than as the default adoption path.

That's completely fine for a large class of teams. It's a non-starter for another.

The trace-to-eval loop is only as adoptable as the place it's allowed to run.

Self-hosting is a capability, not a free lunch

This is where open-source comparisons often become dishonest.

Self-hosting Langfuse is not “run one container and forget about it.” The production architecture means operating the web and worker services alongside the underlying stateful components: ClickHouse, Postgres, Redis/Valkey, and S3-compatible object storage.

That's real operational surface area.

A team without the appetite to run and monitor that stack should think seriously before choosing self-hosting over Langfuse Cloud.

The honest framing is:

You can run the loop entirely on your own infrastructure. That does not mean doing so is operationally free.

The second divergence: framework coupling

LangSmith's loop is strongest inside the LangChain/LangGraph world. Its deepest tracing benefits from knowing the framework's execution model.

Langfuse is more neutral. My test pipeline used the raw Anthropic SDK and a hand-rolled retrieval step, and the workflow didn't care.

If your stack isn't LangChain, framework neutrality stops being a positioning phrase and becomes a practical adoption advantage.

Where Langfuse is not the better pick

If you are already all-in on LangChain/LangGraph, run on managed cloud, and have no meaningful data-residency constraint, LangSmith may simply be the better fit.

Step 1 is nearly free because the framework understands itself. The trace-to-dataset flow is tight. The native execution detail is richer than generic instrumentation can provide.

Choosing Langfuse purely to gain portability you never intend to exercise would be trading away real ergonomic value for an option with no expected use.

Buy the tool that fits the stack you actually have.

The opinion

Stop evaluating these tools on “who has evals” or “who closes the loop faster.”

Both have evals. The loop is table stakes.

The more useful question is:

Do you need to run that loop on your own terms — your infrastructure, your data boundary, your non-LangChain stack?

Yes: Langfuse has the stronger case. The open-source core, first-class self-hosting path, and framework-neutral tracing give you control over where the workflow lives.

No: if you're all-in on LangChain and managed cloud is fine, LangSmith gives you a tighter native experience without paying an operational cost for portability you don't need.

The loop is table stakes. Where it's allowed to run is the actual decision — and that's the line the feature checklist can't show you.

The loop, in code

This is the core of the Langfuse loop I ran: one LLM-as-judge evaluator, one deterministic evaluator, and the experiment call. 

from langfuse.experiment import Evaluation

# LLM-as-judge: is every claim grounded in retrieved context?
def evaluate_groundedness(
    *,
    input,
    output,
    expected_output=None,
    metadata=None,
    **kwargs
):
    verdict = judge(
        context=output["context"],
        question=input,
        answer=output["answer"]
    )

    return Evaluation(
        name="groundedness",
        value=verdict,
        data_type="NUMERIC"
    )


# Deterministic scorer:
# did the model refuse the unanswerable items?
def evaluate_refusal(
    *,
    input,
    output,
    expected_output=None,
    metadata=None,
    **kwargs
):
    if not metadata or metadata.get("answerable", True):
        return []

    refused = bool(
        REFUSAL_PATTERN.search(output["answer"])
    )

    return Evaluation(
        name="refused_when_unanswerable",
        value=refused,
        data_type="BOOLEAN"
    )


dataset = langfuse.get_dataset(
    "qdrant-qa-groundedness"
)

result = dataset.run_experiment(
    name="qdrant-qa",
    run_name="variant-a-terse",
    task=make_task(SYSTEM_A),
    evaluators=[
        evaluate_groundedness,
        evaluate_refusal
    ],
)

Point the same dataset at a second run_name with a different prompt and you have the regression comparison.

That's the mechanism: trace the app, promote failure cases into a dataset, score them, compare runs.

Tested on Langfuse Python SDK v4. LangSmith workflow reconstructed from its published documentation, not run hands-on. August 2026.
