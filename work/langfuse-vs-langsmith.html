Langfuse vs. LangSmith, judged on one workflow: how you get from "I saw a bad answer in production" to "I have a regression test that guards against it."

Hands-on Langfuse · LangSmith researched from current docs · August 2026

Every LLM observability vendor sells you on evals now, and the demo is usually a version of the same thing: here's a trace, here's a score, here's a dataset, look how easy it is to wire them together.

So instead of comparing feature lists, I picked the workflow that I think actually matters once you're operating one of these systems day to day: something bad happens in production, you find the trace, turn that failure into a test case, run a new version of the system against it, and try to make sure it doesn't happen again.

I built that loop end to end in Langfuse, then followed the equivalent workflow through LangSmith's current docs to see where the two diverge.

Less than I expected, it turns out. The loop itself is almost identical — the interesting difference is where you're allowed to run it.

I'm keeping this comparison to two tools on purpose, btw. Phoenix/Arize, Braintrust and generic OpenTelemetry stacks all close some version of this loop too, but Langfuse and LangSmith are the closest all-in-one comparison, and pulling in another five would turn this into a feature matrix instead of answering the question I care about.

Method: what's tested vs. what's researched

There's an asymmetry here, and I'd rather make it explicit than pretend this is a benchmark.

Langfuse: hands-on. I built the full loop myself — instrumented a small RAG pipeline with the Python SDK v4 and OpenTelemetry, captured traces, created an 8-item dataset, wrote two evaluators, and ran two prompt variants with scored runs I could line up side by side. Every Langfuse step below is something I ran.

LangSmith: documentation-based. I traced the equivalent workflow through LangChain's current docs, but I didn't run it against a live account. So I can compare the documented mechanics, but not the things you only learn by living in a tool: how the UI feels after a week, how many clicks it really takes, what quietly breaks in practice.

Where I'm inferring, I say so.

Treat the LangSmith column as "this is what the current docs say the workflow looks like," not "I stopwatch-timed both products and picked a winner." That's a real limitation of this piece, but I'd rather show it than quietly write around it.

Read that table with the asymmetry in mind — I ran the Langfuse column and read the LangSmith one, so I won't pretend to judge UX from this test.

What I can say is narrower but more useful: mechanically, the two loops are very close. Both let you capture a production execution, pull the bad case into a dataset, attach LLM-as-judge or deterministic scorers, rerun the system, and compare against previous variants. There's no magic workflow advantage where Langfuse gets you from "bad answer" to "regression test" in three steps while LangSmith needs twelve.

If anything, for a team already living inside LangChain/LangGraph the friction might lean the other way, since LangSmith already understands the framework's execution model and adding a run to a dataset is about as direct as it gets. Anyone claiming a dramatic difference in step count is probably selling something.

One actual result from the loop

I used the dataset to test a reasonable-sounding hypothesis: if I make the answer prompt more explicit about grounding, the model should produce more grounded answers.

So I wrote a "grounding-hardened" system prompt and ran it against the same 8-item dataset as the terse baseline.

It did nothing.

Both variants scored a perfect 1.00 on groundedness across all 8 items — identical — and both correctly refused the two unanswerable questions. The hardened prompt bought me 38 extra system tokens per call (60 vs 22) for zero measured gain.

I want to be honest about what n=8 can and can't say here, though. Part of this is a ceiling effect: the terse baseline was already at 1.00, so there was nothing left to improve, and a harder dataset that actually produced some partial scores might tell a different story. And "2.7× the system prompt" is true but a bit of a rhetorical trick on my part — 38 tokens is a rounding error next to the retrieved context, question and completion, so it's 2.7× of a tiny number, not a real cost story. The honest conclusion isn't "hardening prompts is useless." It's narrower: on this small, easy set the change moved nothing I could measure — too little to generalize from, but enough to not ship it blind.

That's still one of the reasons I like the trace-to-eval loop. The useful outcome of an experiment isn't always that your clever change worked. Sometimes it's finding out — cheaply, before you roll it out everywhere — that it didn't.

Where they actually diverge: where the loop is allowed to run

Once you've seen the mechanics, the loops are similar enough that the more interesting question moves down a layer: where does all of this actually run?

Because this loop operates on some of the most sensitive data your application has — prompts, completions, retrieved context, metadata, and potentially raw customer input. Architecture stops being an implementation detail the moment you notice that.

Langfuse is MIT-licensed and self-hostable as a first-class path. The same workflow runs in Langfuse Cloud or inside infrastructure you control, so if your production data has to stay within your own boundary, the traces, datasets, evaluators and experiment history can stay there too. For a team handling regulated data — or just data the company would rather not send into another SaaS backend — that shifts the decision a lot. A perfect eval workflow that compliance won't let you point at production data isn't worth much.

LangSmith is proprietary and cloud-first, with self-hosting available at the enterprise level rather than as the normal adoption path. For a huge number of teams that's completely fine. For others it's a hard constraint.

And that's where the comparison gets more interesting than "which one has evals," because the trace-to-eval loop is only useful if you're actually allowed to run it on the data you care about.

Self-hosting is a capability, not a free lunch

This is also where open-source comparisons get a little silly, because "you can self-host it" is usually presented as if someone hands you a Docker command and the problem disappears.

Langfuse self-hosting isn't one container you start and then forget. The production architecture is the web and worker services plus stateful components — ClickHouse, Postgres, Redis/Valkey, and S3-compatible object storage — so there's real operational surface area behind that tidy "self-hosted" box in the comparison table.

Someone has to operate it.

Someone has to monitor it.

Someone gets paged when ClickHouse has opinions at 3am.

So if your team has no actual data-residency requirement and no desire to own another piece of infrastructure, I'd think hard before assuming self-hosting beats just using Langfuse Cloud. The useful distinction isn't:

Open source good, cloud bad.

It's:

You can keep this entire workflow inside your infrastructure if you need to.

That's a capability. Whether you want to exercise it is a separate question.

The second divergence: framework depth, not lock-in

The other difference has less to do with infrastructure and more with what your application already looks like — though it's smaller than vendor positioning implies, and I don't want to overstate it.

It would be easy to write "LangSmith is for LangChain, Langfuse is framework-agnostic," and it would be wrong. LangSmith traces arbitrary Python and JavaScript through its @traceable decorator and provider wrappers, and it ingests OpenTelemetry too, so you can use it with no LangChain anywhere in the stack. Langfuse is equally happy either way — my test pipeline used the raw Anthropic SDK and a hand-written retrieval step, and the eval workflow didn't care.

So this isn't lock-in. The real difference is depth: because LangSmith knows the LangChain/LangGraph execution model, it can show you richer native detail — graph execution, individual nodes — than generic instrumentation can infer from the outside. If your stack is already LangChain, that native awareness is a genuine advantage. If it isn't, both tools are trace-what-you-instrument, and the advantage mostly evaporates.

That's a real distinction, but a narrower one than "framework agnostic" makes it sound on a landing page.

Where Langfuse is not the better pick

Which brings me to the part that usually gets lost in tool comparisons: there are perfectly normal situations where Langfuse isn't the obvious winner.

If your application is already built heavily on LangChain/LangGraph, you're happy running the observability stack in managed cloud, and there's no serious data-residency constraint, LangSmith may be the cleaner choice. The framework already understands itself, so getting the execution structure into the tracing system takes less work, the trace-to-dataset flow is tight, and the native execution detail is richer than what generic instrumentation can infer from the outside.

Choosing Langfuse purely for portability you have no intention of using means trading away real ergonomic benefits for an option that exists mostly in theory. I like optionality as much as the next person, but unused optionality is still something you're paying for somewhere.

Use the tool that fits the system you actually have.

The opinion

I don't think "who has evals?" is a particularly useful way to compare Langfuse and LangSmith anymore.

They both have evals. They both take you from a production trace to a dataset. They both give you deterministic and model-based scoring. They both let you rerun the system and compare experiments. That part is table stakes.

The question I'd ask instead is:

Do you need to run that loop on your own terms — inside your own infrastructure, inside your own data boundary?

If the answer is yes, Langfuse has the much stronger case: the open-source core and first-class self-hosting path let you keep the whole workflow — traces, datasets, evaluators, experiment history — inside your own boundary, and the framework-neutral instrumentation assumes nothing about your stack. If the answer is no — and especially if the application is already LangChain-native — LangSmith gives you richer native execution detail without making you care about portability or infrastructure you don't actually need.

The loop itself isn't really the decision. The environment around it is.

Which, now that I think about it, is usually how infrastructure decisions work anyway.

The loop, in code

For completeness, here's the core of the Langfuse experiment I actually ran: one LLM-as-judge evaluator for groundedness, one deterministic evaluator for refusal behaviour, and the experiment call that runs a prompt variant against the dataset. 

from langfuse.experiment import Evaluation


# LLM-as-judge:
# is every claim grounded in retrieved context?
def evaluate_groundedness(
    *,
    input,
    output,
    expected_output=None,
    metadata=None,
    **kwargs
):
    verdict = judge(
        context=output["context"],
        question=input,
        answer=output["answer"]
    )

    return Evaluation(
        name="groundedness",
        value=verdict,
        data_type="NUMERIC"
    )


# Deterministic scorer:
# did the model refuse the unanswerable items?
def evaluate_refusal(
    *,
    input,
    output,
    expected_output=None,
    metadata=None,
    **kwargs
):
    if not metadata or metadata.get("answerable", True):
        return []

    refused = bool(
        REFUSAL_PATTERN.search(output["answer"])
    )

    return Evaluation(
        name="refused_when_unanswerable",
        value=refused,
        data_type="BOOLEAN"
    )


dataset = langfuse.get_dataset(
    "qdrant-qa-groundedness"
)

result = dataset.run_experiment(
    name="qdrant-qa",
    run_name="variant-a-terse",
    task=make_task(SYSTEM_A),
    evaluators=[
        evaluate_groundedness,
        evaluate_refusal
    ],
)

Point the same dataset at another run_name with a different prompt and you've got the regression comparison.

There's nothing particularly magical about the mechanism, which is kind of the point. Production hands you a failure, the failure becomes a dataset item, evaluators turn the behaviour you care about into something measurable, and experiments tell you whether the next version of the system made it better or just made it different.

The interesting question isn't whether a tool can do this anymore. It's whether it can do it in the environment where your application actually lives.
