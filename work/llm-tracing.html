Technical Writing / LLM Observability

Your LLM trace is a flat log. Here's why that's the problem.

A multi-step LLM application can return the wrong answer while every function succeeds. When nothing crashes, traditional monitoring has very little to tell you.

Your RAG app gave a wrong answer this morning. Nothing threw: a user asked about the refund policy for annual plans and got the monthly policy back, delivered with total confidence.

You check the deploy log and nothing shipped overnight. You check the error tracker and there's no stack trace, because nothing crashed. Every function returned cleanly, which is exactly the problem.

Traditional monitoring exists to tell you that something broke, and here nothing broke. The code ran end to end and produced a bad answer anyway.

Multi-step LLM apps put you in this situation constantly. A pipeline that retrieves documents, then drafts and reviews an answer, has several places to go wrong that all look identical from the outside.

When the final answer is bad, the question that matters is which step is guilty, and a log line can't answer it.

The obvious first move, and why it fails

Most people start by logging the request as one unit: input in, answer out, wrapped in a single log line or one flat trace.

That confirms what you already knew, which is that this input produced this bad output.

Everything in between — the retrieval call, the first model call, the review pass — is collapsed into one opaque blob.

The flat log records the crime without recording the suspects.

You can see that the answer is wrong. You can't see where it went wrong, so your debugging method becomes rereading the prompt and guessing.

Give the trace the same shape as the pipeline

The fix is structural.

Langfuse models an application in nested levels: a session groups related requests, like the turns of one conversation; a trace is one end-to-end request; and inside the trace sit observations, the units of work.

An observation is either a span — any step — or a generation, which is a span specialised for an LLM call and therefore also carries the model name, token counts, and cost.

Here is what that looks like in a real pipeline: 

@observe(name="answer")
def answer(query: str, context: list[str]) -> str:
    # @observe names this step "answer" in the tree;
    # the Anthropic call inside is auto-captured as a generation.
    ...


def run(query: str, session_id: str) -> dict:
    """One end-to-end request = one trace."""

    with propagate_attributes(
        session_id=session_id,
        tags=["pipeline=demo"],
    ):
        with langfuse.start_as_current_observation(
            as_type="span",
            name="rag-pipeline",
            input={"query": query}
        ) as root:

            context = retrieve(query)
            draft = answer(query, context)
            review = critique(query, draft)

            root.update(
                output={
                    "answer": draft,
                    "critique": review
                }
            )

            return {
                "answer": draft,
                "critique": review
            }

Nothing here writes a log message.

The with blocks and @observe decorators declare structure: this request is one trace named rag-pipeline, and everything called inside it hangs off that root.

What you get in the Langfuse UI is a tree with the same shape as the code: rag-pipeline at the root, with retrieve-documents as a plain span alongside answer and critique as named steps.

Each LLM call becomes a generation with its own input, output, latency, token usage, and cost.

The naming is deliberate. Leave the LLM calls to auto-instrumentation alone and they show up under the instrumentor's generic SDK name; the @observe decorator is what makes the tree read like your pipeline instead of like the Anthropic SDK.

The payoff is diagnostic separation.

If retrieval pulled the monthly-plan page instead of the annual one, you have a retrieval bug. No amount of prompt engineering will fix it.

If retrieval pulled the right documents and the answer step still got it wrong, the problem is in the prompt or model, and your embeddings are innocent.

Same bad answer. Completely different fix.

The tree tells you which one you're facing in about thirty seconds instead of an afternoon.

What it costs you

Instrumentation is code, and you own it now.

Auto-instrumentation lowers that cost. The AnthropicInstrumentor used alongside this pipeline captures every model call automatically, with tokens and latency attached, and that's a good default.

But it decides span boundaries for you, and boundaries are where the value lives.

The instrumentor cannot know that retrieve and answer are separate steps in your mental model of the system. Only manual structure can say that.

In practice, the useful combination is:

Auto-instrumentation for the model calls. Hand-written spans for the steps you'll actually debug by.

Restraint matters too. A trace with forty spans for trivial function calls is as unreadable as a flat log.

Nest at the level you'd want to see when something breaks, and no deeper.

Why not just raw OpenTelemetry?

Langfuse is built on OpenTelemetry, and you can point generic OTel spans at another backend.

What you give up is the LLM-shaped layer on top: generations that natively understand models, tokens, and cost, and a UI that renders a prompt and completion as first-class objects instead of as a flat attribute bag.

If you don't need that layer, plain OpenTelemetry is a legitimate choice. If you do, rebuilding it yourself is the expensive path.

The less optional caveat: data boundaries

Tracing often ships full model inputs and outputs to the observability backend.

In the refund-policy example, that may mean customer text and internal policy content leaving your application boundary.

Masking or excluding sensitive fields before they hit the span is therefore a first-class design decision, not a cleanup task for later.

It is one of the first questions a security review will ask.

Where this leaves you

Structure is what turns:

“The answer is wrong”

into:

“The retrieval step is wrong.”

That sentence is the difference between guessing and debugging.

It also compounds. The same tree you built for debugging is the structure that evaluations and per-step cost attribution attach to later.

Get the shape right first, and the rest of observability has somewhere to live.
