Technical Writing / LLM Observability

Your LLM trace is a flat log. Here's why that's the problem.

A multi-step LLM application can return the wrong answer despite every function succeeding. When nothing crashes, traditional monitoring has very little to tell you.

Sometimes it happens - your RAG app gave a wrong answer this morning. Nothing threw: a user asked about the refund policy for annual plans and got the monthly policy back, delivered with usual total confidence.

You check the deploy log - nothing shipped overnight.

You check the error tracker - there's no stack trace, because nothing crashed.

Every function returned cleanly, and that’s the problem.

Traditional monitoring exists to tell you that something broke, but what do you do when nothing broke? The code ran end to end and produced a bad answer anyway.

The situation is very familiar to any multi-step LLM apps devs. There are several failure points in a workflow that retrieves documents, drafts an answer, reviews it - and from the outside, they all look identical.

When the final answer is bad, the question is which step is guilty, and a log line can't answer it.

The obvious first move - and why it fails

Most people start by logging the request as one unit: input in, answer out, wrapped in a single log line or one flat trace.

That confirms what you already knew, which is that this input produced this bad output.

Everything in between - the retrieval call, the first model call, the review pass - is mixed together in one blob.

You can see that the answer is wrong. You can't see where it went wrong, so your debugging method becomes rereading the prompt and guessing.

The flat logs aren’t helpful.

Give the trace the same shape as the pipeline

The fix is structural.

Langfuse has a simple hierarchy: a session groups related requests, a trace is one end-to-end request, and observations are the individual steps inside it.

An observation can be a normal span, or a generation - an LLM call with things like the model, token usage, latency and cost attached.

For a small RAG pipeline, I want the trace to look roughly like the pipeline itself: 

@observe(name="answer")
def answer(query: str, context: list[str]) -> str:
    # @observe names this step "answer" in the trace.
    # The Anthropic call inside is captured automatically.
    ...


def run(query: str, session_id: str) -> dict:
    """One request = one trace."""

    with propagate_attributes(
        session_id=session_id,
        tags=["pipeline=demo"],
    ):
        with langfuse.start_as_current_observation(
            as_type="span",
            name="rag-pipeline",
            input={"query": query}
        ) as root:

            context = retrieve(query)
            draft = answer(query, context)
            review = critique(query, draft)

            root.update(
                output={
                    "answer": draft,
                    "critique": review
                }
            )

            return {
                "answer": draft,
                "critique": review
            }

There are no log messages here.

The with blocks and decorators are just describing the structure of the request.

One request becomes rag-pipeline. Inside it sit retrieval, answer and critique, together with the actual LLM calls that happened inside those steps.

So when you open the trace, you see something close to the system you actually built.

And this is where tracing becomes useful.

Go back to the refund-policy example.

If retrieval returned the monthly-plan document instead of the annual one, you have a retrieval problem. Changing the system prompt is not going to help.

If retrieval returned the correct documents and the model still produced the monthly policy, retrieval did its job. Now you look at the prompt, model or surrounding answer logic.

Same wrong answer.

Very different bug.

That distinction is what the trace gives you.

Naming the steps

There is one small detail that matters more than I expected.

If you rely entirely on auto-instrumentation, model calls often appear under generic SDK names.

That is technically accurate, but not particularly useful when you are trying to understand the application.

The @observe(name="answer") decorator makes the trace describe your pipeline, rather than the SDK underneath it.

I want to open the trace and see retrieve, answer, critique.

Seeing three generic Anthropic calls tells me much less.

What it costs you

Of course, instrumentation adds code.

Auto-instrumentation removes a lot of the boring part. The Anthropic instrumentor can capture the model calls, latency and token usage automatically, which is exactly the kind of thing I would rather not wire manually.

But it cannot understand the architecture of your application for you.

It doesn't know that retrieval and answer are separate failure points. It only knows that some functions and API calls happened.

You still have to define the boundaries that matter.

The combination I ended up liking is:

Auto-instrument the model calls. Add manual spans around the steps you would actually want to debug.

There is also such a thing as too much tracing.

If every small helper function becomes a span, the trace stops helping. You just get a very elaborate tree that you now also have to read.

I think the right level is fairly practical: if this step failed, would I want to inspect it separately?

If yes, give it a span.

If not, probably don't.

Why not just use OpenTelemetry?

You can.

Langfuse itself uses OpenTelemetry underneath, and generic OTel spans can be sent to plenty of other backends.

What Langfuse adds is an LLM-specific layer.

A model call is not treated as just another span. It has prompts, completions, model metadata, tokens and cost, and the UI knows how to display those things.

You could model all of this yourself with raw OpenTelemetry.

Whether that is worth doing depends on what you need.

If you mainly want normal distributed tracing, plain OTel may be enough.

If the thing you are debugging is usually an LLM call, having a backend that already understands LLM calls is convenient.

The less fun part: data

Useful traces often contain quite a lot of data.

Prompts. Model responses. Retrieved documents. User input.

In the refund-policy example that could already mean customer text and internal policy content being sent to the observability backend.

In production systems, the data can obviously be much more sensitive.

So what gets captured, masked or excluded needs to be decided when tracing is designed, not after it has already been running for a month.

The observability system can potentially see the same data your model sees.

That should be treated accordingly.

Where this leaves us

Flat logs are not useless.

They are great for things like exceptions, failed connections, process state and obvious latency problems.

They are just not enough to explain a system where the code can execute successfully and the result can still be wrong.

For that, you need the structure of the execution.

The useful transition is:

“The answer is wrong.”

to:

“Retrieval returned the wrong document.”

Now you have somewhere to start.

And the structure becomes useful beyond debugging.

The same trace tree is where you can later attach per-step latency, cost, evaluations and production examples that become regression tests.

But those things only become useful once the underlying trace actually represents the application.

So I would start there:

Make the trace look like the system you are trying to understand.
